# 보안점검 (15대 보안통제)

점검 항목 정의는 `references/checklist.md`. 시작 전에 반드시 읽는다.

## 원칙

- **읽기 전용.** 코드·설정·작업트리를 바꾸지 않는다(checkout·stash 금지). 결과 md 1개만 쓴다.
- **근거 없는 판정 금지.** 모든 판정에 `파일경로:라인` 근거를 단다. 코드로 확인되지 않으면 "확인필요"로 두고 누구에게(인프라·보안·IdP·GitHub 조직 관리자 등) 무엇을 확인할지 적는다.
- **판정값:**
  - 양호 / 취약 / 확인필요
  - NA — 해당 기능 자체가 없음(예: 파일 업로드 기능 없음)
  - NA(타 시스템) — 이 저장소가 아니라 연동 서버·인프라에서 점검할 항목. 비고에 어느 시스템인지 적는다.
- **비밀값을 화면·로그에 내지 않는다.** 결과 md는 물론 작업 중 도구 출력에도 원문이 찍히지 않게 한다.
  - 비밀 탐색은 `grep -rnE '<패턴>' . | cut -d: -f1,2` 처럼 **파일:줄 번호만** 뽑는다. 해당 파일을 `cat`하거나 매칭 줄 전체를 출력하지 않는다.
  - 원격 URL은 `git remote get-url origin | sed -E 's#://[^@/]+@#://***@#'` 로 마스킹해서 보고, 자격증명 포함 여부만 판정한다.
  - 결과 md에는 위치와 종류만 적는다(`application-dev.yml:12 DB 비밀번호 평문`).

## 절차

1. **대상 유형 판별** — 저장소마다 아래 셋 중 하나로 분류하고 근거를 적는다. 유형별로 보는 관점이 다르다(아래 "유형별 관점").
   - **서버 서비스**: 웹 프레임워크·HTTP 엔드포인트가 있음(Spring, FastAPI, Express 등)
   - **클라이언트 앱**: 데스크톱(Electron 등)·모바일·IDE 플러그인. 서버는 따로 있음
   - **배포물**: CLI, 스킬·플러그인 저장소, 라이브러리, 설치 스크립트. 사용자 PC에 복사·실행됨
   스택(build.gradle/pom.xml, pyproject, package.json 등)과 인증 방식(자체 로그인 / 외부 IdP / API Key·라이선스 키 / 없음)도 같이 정리한다.
2. **점검 리비전 고정** — `git fetch` 후 현재 브랜치와 behind 커밋 수를 확인한다. 실제 배포 기준 브랜치(main/develop 등 — 모호하면 사용자에게 묻는다)와 다르면 `git worktree add <임시경로> origin/<브랜치>` 또는 `git archive`로 임시 디렉터리에 꺼내 점검하고, 끝나면 임시 디렉터리를 정리한다. 결과 md 상단에 점검한 브랜치·커밋을 적는다.
3. **항목별 점검** — 아래 힌트를 참고해 검색·열람한다. 저장소가 크면 항목 묶음별로 서브에이전트에 나눠 맡겨도 된다(인증/권한 #3·#4, 인젝션 #5, 비밀정보 #2·#8, 파일·로그·자동화 #9~#11).
4. **기존 진단 결과 확인** — 저장소나 사용자가 알려준 위치에 최근 1년 이내 보안성 검토/모의해킹/취약점 진단 결과가 있으면 해당 항목 비고에 "진단 결과로 대체 가능"과 출처를 적는다.
5. **결과 작성** — 아래 출력 형식으로 저장하고, 요약표를 사용자에게 보여준다.

|------|------------------------|---------------------------|
| 서버 서비스 | 없음(전 항목 대상) | — |
| 클라이언트 앱 | #3·#4·#10·#11-1 은 대개 NA(타 시스템: 연동 서버) | 창 이동·새 창 제어, preload/IPC 노출 범위와 발신자 검증, sandbox·contextIsolation·nodeIntegration → **#5-1** / DevTools·디버그 메뉴 운영 노출, 로컬 포트 바인딩 → **#1** / 배포 패키지(asar 등) 내 소스맵·비밀값, 로컬 토큰 보관 방식 → **#2·#8** / 앱 코드서명, 자동 업데이트·확장 다운로드의 서명·체크섬·https 강제 → **#9** / 런타임 버전 지원 종료(Electron 등) → **#5-1** 비고 |
| 배포물 | 서버 통제 항목 대부분 NA | 설치·업데이트 시 원격 스크립트 실행, 사용자 설정·훅 변경, 버전 미고정 자동 패키지 설치 → **#5-1** / 사용자 입력 이름·경로를 `rm`·`cp`에 쓰는 경로 조작 → **#11-2** / main 직접 push·브랜치 보호 부재 등 공급망 → **점검표 외 추가 관찰** |

인증이 ID/PW가 아닌 경우(라이선스 키·API Key) #6은 키 발급·만료·폐기·추측 가능성(공용 개발 키의 운영계 유효 여부) 관점으로 보고, 코드로 판단이 안 되면 확인필요로 둔다.

## 항목별 점검 힌트

| # | 볼 곳 |
|---|------|
| 1 | 관리자 경로(`/admin`, 관리 화면 라우트), actuator·swagger·h2-console·debug 엔드포인트의 노출 여부와 인증 요구 여부, Ingress/게이트웨이 설정 |
| 2 | `.gitignore`, 저장소에 커밋된 백업·덤프·`.env`·키파일, 설정파일에 내부 IP·도메인이 하드코딩인지 환경변수(`${...}`)인지, 정적 리소스 경로에 설정파일이 섞여 있는지. **배포 산출물이 있으면 풀어서**(jar·asar·wheel·dist 목록) 소스맵·테스트·설정·키 패턴 포함 여부를 확인 |
| 3·4 | 리소스 ID를 경로/쿼리로 받는 API마다 현재 사용자 기준 소유권·권한 검증이 서버에 있는지(IDOR). Spring: `SecurityConfig`의 `permitAll`, `@PreAuthorize`, 서비스 계층의 소유자 비교. FastAPI: `Depends` 인증, 쿼리 where에 사용자 조건. 프론트만 막고 서버가 안 막는 경우는 취약 |
| 5-1 | `eval`/`exec`/`Runtime.exec`/`ProcessBuilder`/`subprocess(shell=True)`/`spawn(shell:true)`/템플릿 엔진에 사용자 입력 유입 |
| 5-2 | 문자열 결합 SQL, MyBatis `${}`, JPA native query + 문자열 결합, Python f-string SQL, `ORDER BY` 동적 컬럼 |
| 5-3 | `RestTemplate`/`WebClient`/`requests`/`httpx`/`fetch`에 사용자 입력 URL·호스트가 들어가는지, allowlist 유무 |
| 5-4 | 허용 HTTP Method(TRACE/OPTIONS 등), CORS `allowedMethods`·`allowedOrigins("*")`, WAS·Nginx 설정 |
| 6·7 | 자체 인증이면 패스워드 정책·잠금·MFA·자동로그인 구현 위치. 외부 IdP면 그 사실과 설정 위치만 적고 확인필요. Default·공용·서비스 계정 seed 데이터 |
| 8 | 세 군데를 모두 본다: ① 추적 파일 ② **git 이력**(`git log -p --all -S '<키워드>'`, `git log --all -G '<정규식>' --format=%h` — 원칙의 출력 제한을 지킨다) ③ **커밋 안 된 로컬 파일**(`git status --ignored --porcelain`, `git ls-files --others`)과 그 파일이 `.gitignore`에 빠져 있는지. 키워드: password, secret, apiKey, api_key, token, license, `sk-`, `AKIA`, `ghp_`, `-----BEGIN`. 문서(docs·spec·plan md)도 대상. 이력에서 나온 키는 "값 교체가 아니라 폐기·재발급" 으로 조치 방안을 적는다. 저장소 공개 여부: `gh repo view <org/repo> --json visibility` → 안 되면 익명 `curl -sI https://github.com/<org>/<repo>` 상태 코드(404면 private 추정) → 그래도 불명확하면 확인필요(GitHub 조직 관리자) |
| 9 | 업로드 확장자 화이트리스트, MIME 검증, 저장 경로가 웹 실행 경로 밖인지, 파일명 재생성 여부. 클라이언트 앱은 "받아서 실행하는 파일"(업데이트·확장·플러그인)의 서명·체크섬 검증으로 해석 |
| 10 | 인증 성공/실패·권한 변경·조회·다운로드 감사로그 기록 위치와 필드(ID·일시·IP·수행업무), 보관 기간 설정, 로그 접근 통제 |
| 11-1 | rate limit(Bucket4j, slowapi, 게이트웨이 정책 등), 대량 요청 차단 로직 |
| 11-2 | 다운로드·압축 해제·삭제 경로에 사용자 입력이 들어갈 때 `..` 차단·정규화(`normalize`/`realpath` 후 기준 디렉터리 prefix 검증), zip-slip·심링크 검사 |
